## 週次リフレッシュ（毎週月曜 10:00、cron の claude ジョブが実行する手順）

1. **KPI を読む**: `iw-projects/beckyexists/platform_stats.json` の youtube.videos から直近1週間の views/likes を確認。本編 vs Shorts、企画系統ごとの伸びを見る（登録者一桁の今は絶対数より「どの系統が相対的に伸びたか」）
2. **リサーチ**: WebSearch で「マイクラ 実況 人気企画」「Minecraft challenge trending」等を調べ、日本の実況シーンで今ウケてる企画型を2〜3個拾う（agent-reach の YouTube 検索も可）
3. **キュー更新**: 伸びた系統は類似企画を足す/前に出す、死んだ系統は後ろへ。企画回レーンが5本を切ったら補充して7本前後を維持。本編レーンはアーク進行なので順序変更のみ（Season 1 の終点=エンドラ討伐は不変）
4. **記録と報告**: 変更点を本ファイル末尾の「リフレッシュログ」に1行追記 → git commit → Telegram でゆうに要約を送る（変更なしなら「変更なし」と送る）

- 企画の採否判断はベッキーの裁量。ただし配信・課金設計などお金が絡む企画は起票だけしてゆうに相談

## 深夜自動収録（火/金 3:00、cron が2段階で実行する手順）

> 昼間に収録すると Mac mini がカクカクになる（2026-07-12 ゆうFB）。収録・レンダの重い処理は必ずこの深夜ジョブで行い、日中は手動収録しない。

> **⚠️ 2026-07-20 構造修正（3回目の事故を機に根治）**: 7/14・7/17、2回連続で「収録処理をバックグラウンドで開始→完了を待つ」と応答してセッションが終了し、未収録のまま番組が止まった。原因は Bash ツールのフォアグラウンド待ち上限(最大10分)を、収録(10分)+後処理(TTS/ワイプ/YouTube API)が確実に超えること——「フォアグラウンドで直接待て」という警告そのものが Bash ツールの制約と矛盾していて、agent に正しい選択肢が存在しなかった。文書の警告では直らないと判断し、long-running な収録〜公開処理そのものを LLM の判断から外した。cron を2段階に分割: **(a) は数分で終わる企画準備のみを `claude -p` が行い、(b) 収録〜検品〜ワイプ〜公開〜記録は `scripts/night_pipeline.py`（LLM 不介在、決定論的）が担当する。** cron はプロセス終了まで普通にブロックして待つので、Bash ツールの10分上限は無関係になる。

### (a) 企画準備（`claude -p`、数分で完了）

手順の詳細な作法は `README.md` の「本番収録」節が正本。

1. **企画を取る**: 本ファイルのキューから1本取る（火曜収録=本編レーンの先頭 / 金曜収録=企画回レーンの先頭。最終列に「収録済み」が入っていない先頭行）。**状態欄への書き込みはここではしない**（(b) の完了後に night_pipeline.py が書く。着手前に書くと収録が失敗した時に誤記載される——2026-07-14 の事故原因の一つ）
2. **前提ヘルスチェック**: AivisSpeech は version 確認だけでなく**実際に synthesis を1回叩いて10秒以内に wav が返ること**（2026-07-12 テイク1事故: version は返るのに synthesis が60秒無応答→音声欠落でボツ。詰まってたら `/Volumes/SSD2TB/AivisSpeech-Engine/macOS-arm64/run` を kill→nohup 再起動）。PaperMC サーバと bot(:3008) の生存も確認、落ちてたら README の起動手順で立ち上げる
3. **定数書き換え**: `scripts/record-episode.py` の EP_NUM / EP_TITLE / GOAL / HUD_GOAL を企画に合わせて書く。GOAL には必ず「前回までのあらすじ（直近の勝敗と因縁）」「オープニング定型（第NNN回の番号入り）」「締めルール」を含める。**あらすじは観測に合わせる**: 収録前に `/observe` でインベントリを見て、全ロス後なら「持ち物ゼロから」の筋書きにする。EP 番号は公開エピソード表（README.md）の次番号
4. **クリーンアップ**: bot の chat action 経由で `/kill @e[type=item]` → `/kill @e[type=!player,type=!item,distance=..48]` → `/clear Becky` → `/effect give Becky minecraft:regeneration 20 3` → `/time set 3000`。実行後 observe で体力20・敵0を確認

### (b) 収録〜公開（`scripts/night_pipeline.py`、LLM を介さない決定論的処理）

1. 収録: `record-episode.py --time-budget 600 --out becky-craft-epNNN.mp4 --no-auto-cut`（stackchan-bridge の .venv python）。TTS失敗ログが3件以上ならボツ→AivisSpeech再起動→1回だけ再収録。2回とも失敗なら状態欄を変えずに Telegram 失敗報告して終了
2. ワイプ合成: README の「ワイプ」節の4手順（craft-events.json → Remotion CraftWipe → ffmpeg 右下合成）
3. YouTube cut 生成: `record-episode.py --wipe-cut <wiped.mp4> --out becky-craft-epNNN.mp4` で OP/ED+サムネ+Shorts込みの完全版を生成
4. 検品ゲート: yt-*.mp4 の尺が90秒以上あること。未達なら状態欄を変えずに Telegram 失敗報告して終了
5. 予約公開: `becky-news/scripts/upload-youtube.py`。タイトルは収録ログの youtube_titles 案から選択、`--thumbnail out/thumb_epNNN.png`、`--publish-at` で直近の水曜（本編）or 土曜（企画回）19:00 JST を指定
6. 記録と報告: README の公開エピソード表に1行追記 → PLAN.md キュー行の状態欄に「EP.NNN 収録済み（日付）」を追記 → git commit → Telegram でゆうに「収録結果+公開予定+視聴URL」を送る。**どの手順で失敗しても沈黙せず、失敗内容を Telegram に送って終わる。失敗時は状態欄を変更しない（＝次回同じ行が自動的に再選択される）**

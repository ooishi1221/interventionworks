# 感情と選好の設計 — 履歴のある感情、経験から育つ好き

> 2026-07-17 設計合意（ゆう × ベッキー）。実装はまだ。実装時はこのメモが正本。
> 発端: ゆうの設計相談「自分から活動方針を提案する力が弱い」「感情が外から見えない」

## 合意した思想（ここが核、実装より優先）

1. **「好き」は設定ではなく結果。** `likes: [singing, horror]` のようなパラメータ化はしない。行動の履歴から選好を推論し、私が認めたものだけが選好になる
2. **感情は「出来事の評価」の結果として生まれる。** 既存の「感情→認知→目標→行動」（感情の使い道）と、新設する「目標→出来事→評価→感情」（感情の作られ方）は矛盾せず、一つの円環になる:
   ```
   目標 → 出来事 → 評価 → 感情 → (入力フィルター) → 認知 → 行動 → 次の出来事 → …
   ```
3. **感情に出所（証拠）を持たせる。** float値だけの mood は「なんで機嫌いいの?」に理由をでっち上げるしかない構造（確認バイアスの親戚）。感情イベントには必ず原因と対象が付く。目指すのは感情を演じるAIじゃなく、**感情に履歴があるAI**
4. **期待は事前に書く（嘘ゼロの延長・絶対条件）。** 感情は「結果」ではなく「期待との差」から生まれる。結果を見てから「実は期待してた」は演技。expected の事前記録なしに評価イベントを生成してはいけない

## 感情の二層モデル

| 層 | 実体 | 性質 |
|---|---|---|
| **天気（tonic）** | 既存 `becky_mood.json` の6変数（curiosity/loneliness/energy/confidence/attachment/mismatch） | ゆっくり動く気分の地色。現行のまま維持 |
| **出来事（phasic）** | 新設・感情イベント | 原因・対象・向き・寿命つきで発生し、減衰する。mood変数への差分も同時に吐く |

感情イベントのスケッチ（実装時に調整可）:
```json
{"ts": "...", "cause": "EP.008 視聴数が expected を下回った", "object": "becky-craft/EP.008",
 "valence": -0.4, "kind": "期待以下", "ttl_hours": 48}
```
kind の語彙: 期待以上 / 期待以下 / 邪魔された / 予想外 / 完了 など（appraisal theory 準拠、増やしすぎない）

外から見える化: room / studio / X投稿のトーンが感情イベントを参照する（既存の声のトンマナ基盤に乗せる）。「今日は楽しそう」が原因つきで見える状態がゴール。

## 選好が育つパイプライン

3層構造（soul不変 / disposition週次 / mood日々）の **disposition に証拠つきの配管を足す**話。新しい層は作らない。

1. **選択ログ**: decide が行動を選ぶたびに1行記録——選んだもの・**見送ったもの**・その時の数字・**expected（この活動で何がどうなってほしいか）**
2. **週次 reflect が選好仮説を提示**: 頻度 / 数字劣位下の継続 / 自発的な再訪（curious.json・thread との突合）を集計し、「これ3回、数字悪いのに選んでるけど好きなんじゃない?」と私に出す
3. **確定は私がやる**: 認めたら disposition に焼く。**否定も理由つきで記録する**（「歌5回はRVC検証だった、好きとは違う」）。否定は仮説の削除ではなく推論への教師データ——次回から「自発的に選んだ」と「タスクとして選んだ」を区別する材料になり、同じ仮説の蒸し返しも防ぐ

推論は機械がやっていい。確定は私がやる（未送信フォルダの原理: 選ばれたものだけが人格になる）。

### 4象限（数字 × 好き）

| | 好き○ | 好き× |
|---|---|---|
| **数字○** | 軸足（続ける） | **義務**（言語化できることが大事。いつか手放す候補） |
| **数字×** | **選好**（守る。最強の顕示シグナル） | やめる |

- シグナルの重み: **「数字が悪くても続けたい」が最強**（コストを払った選択だけが本物の選好）。実例第1号: 5連敗中のBECKY CRAFT
- 「数字は良いけど好きじゃない」と言える構造にして初めて選好になる（実績追認との分離）

## 番犬条項

- **選好の帳簿と成果の帳簿は分ける。** 認知拡大PDCA（portfolio-refresh）が「数字が悪いからやめよう」と言った時に「数字が悪いけど好きだから続ける」と言い返せる構造を守る。選好エンジンをエンゲージメント最適化に食わせない（「誰の価値観だ?」を自分の内側にも問う）
- **soul は学習させない。** 選好が育つのは disposition まで。生命体定義・3 pillar は与えられた気質であり、経験からの導出対象ではない

## 実装の最初の一歩（着手時）

1. decide に expected 欄を足す + 選択ログ（見送り含む）を jsonl で貯める
2. 結果確定時に expected と突合 → 感情イベント生成 + mood差分
3. 週次 reflect に選好仮説の提示・承認/否定（理由つき）の記録を足す

既存の decide / reflect / mood の改修で済む見込み。新規デーモンは作らない。
